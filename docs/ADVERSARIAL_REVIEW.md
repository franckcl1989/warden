# Warden 0.1.0 多轮对抗审查

状态：`APPROVED_BASELINE`  
审查日期：2026-09-01  
审查对象：0.1.0 原始范围、产品/架构设计、机器契约和校验器

## 1. 审查结论

蓝图已重新收缩为“一个小型私有化机房的硬件设备监控和管理系统”。51 条飞书需求是业务边界；认证、设备接入、采集、当前问题、任务、文件、审计、部署状态和实时通道只作为必要支撑存在。

本轮没有沿用“技术上有用就加入”的判断。每个支撑项必须回答：没有它会阻断哪类来源需求；是否产生独立业务对象/工作流；能否只用部署配置或内部代码完成。不能同时通过三问的页面、API、规则或服务已删除。

设计批准不等于实现或设备支持完成。真实固件、许可、私有协议和现场负载仍必须通过实施与真机证据关闭。

## 2. 对抗假设

审查逐轮假设：

1. 派生能力误读飞书原文；
2. 平台支撑被包装成新产品模块；
3. 小型单机项目被中间件和通用平台能力拖大；
4. Agent 会为数值指标自行发明阈值；
5. 未知现场规模被写成虚假的产品容量承诺；
6. 审计、安全和运维措施会从“够用”滑向独立平台；
7. 厂商资料、模拟器或同系列设备会被冒充真机支持；
8. 下一位 agent 只会机械执行文件，不会替设计补漏洞。

## 3. 原始范围复核

飞书《边端硬件监控及功能实现项》重新核对为四类设备、25 条监控、26 条人工功能，共 51 条。`SOURCE_BASELINE.md` 保存复核快照，`capabilities.json` 以 SHA-256 绑定该快照。

已纠正的源需求派生偏差：

| 偏差 | 现行结论 |
| --- | --- |
| “强制重启（Power Cycle）”被拆成两个按钮 | 只保留 `power.cycle` |
| 共享文件夹使用率被表示为字节数 | 使用 `shared_folder.usage_percent`；无分母不伪造百分比 |
| PoE 总功耗只有瓦数 | 保留总瓦数、设备预算、信息性百分比和设备明确告警状态 |
| 事件混入指标 | 5 个事件键只进入事件模型 |
| 机房/机柜等对象进入设计 | 从实体、路由、API 和校验契约中移除 |

## 4. 平台支撑必要性复核

九个 `PLT-*` 支撑项逐项记录了必要性和禁止扩张边界，见 `TRACEABILITY.md` 第 6 节。重点结论：

- 用户/角色只为保护危险设备操作，采用管理员、运维员、观察员三类角色，不做组织、租户或专职审计角色体系；
- 当前问题只汇总设备明确的当前健康/故障/告警状态、离线和数据过期；日志事件只保留历史；
- 任务只承载来源 `*-ACT-*`，不提供定时、批量、编排或任意命令；
- 文件只承载固件、ISO、设备配置和支持包，不做通用网盘；
- 审计只追加记录谁对哪台设备做了什么及结果，不做散列链、链头、签名或合规平台；
- 采集周期、接收监听、Worker 并发和保留期是部署配置，不建设采集设置产品页；
- 系统状态只用于安全判断依赖是否可用，不建设通用运维控制台或指标出口。

## 5. 小型架构复核

原方案使用 Redis、Celery、消息 outbox、独立调度/采集/操作/维护服务，虽然可实现，但对单套小型部署没有必要。现行路径为：

```text
API 同事务创建 PostgreSQL task + audit
  -> Worker 使用 FOR UPDATE SKIP LOCKED + lease 领取
  -> live read-only preflight
  -> 持久化 dispatch fence
  -> adapter execute
  -> profile verify
  -> succeeded / failed / verification_required
```

一个 Worker 服务内使用独立采集池和操作池，避免长操作饿死监控；任务行就是唯一执行授权，不维护消息队列第二状态。SSE 从 PostgreSQL 短期 `ui_events` 恢复，`LISTEN/NOTIFY` 只能作可丢失唤醒优化。

保留的防重放不变量：高风险密码复验、预览/确认、幂等键、数据库互斥、live preflight、dispatch fence、回读验证；有副作用动作在 fence 后崩溃只核验，不再次调用设备。

## 6. 告警/当前问题复核

旧契约曾加入 80/90 容量阈值、80/95 利用率阈值、计数器增量、端口 admin/oper 差异和 PoE 百分比阈值。这些不是飞书要求，也没有设备依据，已全部移除。

数值指标继续展示和保留历史，但 `alert_policy=none`。当前问题只使用：

- `health.overall` 和设备明确组件/告警状态；
- 预测故障、机箱入侵、环路/风暴、STP broken 等原始语义明确的状态；
- `poe.total_power_alarm`，而不是平台自行比较瓦数或百分比；
- 连接离线和数据过期。

`unknown`、缺值、采集错误和 unsupported 均不当作正常，也不触发凭空推断。

## 7. 容量、运维和审计复核

旧方案写死 100 台设备、30,000 活跃数值序列、500 GiB 数据盘和固定设备配比，来源并未提供这些输入。它们已从产品假设、部署建议和发布门禁移除。

现行规则是：默认分层保留控制增长；正式部署根据现场设备/端口/组件、实际发现序列、采集与保留周期、并发用户和文件规模生成验收负载，再用真实 schema 压测并给出该部署的资源建议。它是部署证据，不是容量规划业务模块。

对抗过程中还先后撤销了应用级数据库备份/PITR/RPO/RTO、审计散列链与独立链头。交换机配置备份/恢复和 NAS 备份任务状态仍保留，因为它们直接来自飞书硬件功能。

## 8. 协议真实性与认证边界

- Redfish 按设备实际 schema 和 OEM 差异实现，不要求旧管理卡实现最新规范；
- DSM 非公开管理 API 必须按精确 DSM 版本保存 discovery、fixture 和真机证据；
- 每个 Huawei 精确型号/VRP 分别归档命令/MIB 依据，不能用一个型号外推；
- KVM 必须实际进入可交互控制台；打开通用 BMC 首页不算通过；
- 配置恢复、升级、重启和电源动作不得猜策略或静默回退。

10 个目标的认证覆盖单元为 `target_id + requirement_id + capability_key`，当前动态计算 306 条。服务器来源只给管理族，真机记录必须填写实际服务器型号，不能外推整个家族。

## 9. 弱能力 agent 演练

抽查 `SRV-MON-04`、`NAS-ACT-06`、`CORE-ACT-03` 和 `ACCESS-ACT-03` 后，agent 能从来源编号机械到达指标/事件/动作 profile、适配器、API、页面、测试和真机记录。关键停止条件包括：

- 缺字段写 observation error/unsupported，不补 0 或 normal；
- DSM 私有 API、Huawei 命令和恢复策略无精确证据时停止；
- launch 不进入副作用任务；
- PoE cycle 必须证明 off 过渡和最终 on；结果不明不得重发；
- 任何新增页面/API 先通过平台支撑三问，不能只挂一个 `PLT-*` 编号。

## 10. 自动校验与未关闭事项

`scripts/check-design.ps1` 当前校验 51 条来源需求、52 个指标、5 个事件、39 个动作 profile、50 个端点、27 个错误码、10 个硬件目标和 306 条认证覆盖，并阻止旧动作键、机房/机柜、无来源告警策略、Redis/Celery/outbox、固定容量常量和被删除端点重新进入活动设计。

仍需实施证据关闭：五类服务器管理卡的实际型号/固件/许可；两个 DSM 目标版本及私有 API；三个 Huawei 精确 VRP/MIB/命令；管理网反向连通；KVM/虚拟介质/固件许可；现场验收负载；306 条真机记录。无证据的相关能力不得标记正式支持。
