# Warden 设计决策记录

状态值：`accepted`、`superseded`、`proposed`。只有 `accepted` 是当前约束；`superseded` 仅保留历史原因，禁止按其“决策/结果”实施，必须继续读取后续替代 ADR。

## ADR-000：废弃早期逐项草案

- 状态：`accepted`
- 日期：2026-09-01
- 决策：2026-09-01 之前形成的逐项页面/权限草案全部作废，以本次完整重设计文档为准。
- 原因：早期草案将可能有用的概念当成必需能力，出现机房/机柜等范围漂移，且缺少从设备需求到适配器和测试的闭环。

## ADR-001：飞书矩阵是硬件业务能力唯一来源

- 状态：`accepted`
- 日期：2026-09-01
- 决策：0.1.0 中所有人工触发的硬件操作必须对应 `PROJECT_SPEC.md` 第 2 节的需求编号。
- 结果：文档外只允许新增承载需求所必需的平台支撑，不新增业务动作。

## ADR-002：面向单套小型私有部署

- 状态：`accepted`
- 日期：2026-09-01
- 决策：0.1.0 采用单套 Docker Compose 部署，不设计多租户、机房/机柜层级、高可用集群和 Kubernetes。
- 原因：与“小型私有化机房”目标一致，并降低部署和维护成本。

## ADR-003：统一能力模型与厂商适配器

- 状态：`accepted`
- 日期：2026-09-01
- 决策：平台使用稳定的能力键和统一返回语义，所有 Redfish、DSM、SNMP、SSH、Telnet 和厂商 OEM 差异只存在于设备适配层。
- 结果：API 和 UI 不直接依赖厂商命令；设备不支持时返回明确能力状态。

## ADR-004：观察路径与变更路径分离

- 状态：`accepted`
- 日期：2026-09-01
- 决策：监控采集为可重试的读取任务；人工硬件操作为持久化的副作用任务，结果不明时不得自动重放。
- 结果：操作任务增加 `verification_required` 状态，并使用幂等键防止重复提交。

## ADR-005：技术栈基线

- 状态：`superseded`
- 日期：2026-09-01
- 决策：Vue 3 + TypeScript + Vite 构建前端；FastAPI + SQLAlchemy + Celery 构建 API 和任务；PostgreSQL 18 保存权威数据；Redis 仅作队列和短期协调；Nginx 统一入口；Docker Compose 私有化部署。
- 原因：前端适合高交互监控界面，Python 设备协议生态成熟，任务队列能隔离长时间硬件操作，PostgreSQL 提供可靠事务和灵活 JSONB。

## ADR-006：不代理厂商 KVM/DSM/Web 页面

- 状态：`accepted`
- 日期：2026-09-01
- 决策：KVM、DSM 和设备 Web 管理使用受控启动描述符打开设备页面，不通过平台 iframe 或反向代理注入凭据。
- 原因：不同厂商的 CSP、证书、WebSocket 和插件机制差异大，代理会扩大凭据泄露和兼容性风险。

## ADR-007：浏览器终端只用于交换机 SSH/Telnet

- 状态：`accepted`
- 日期：2026-09-01
- 决策：SSH/Telnet 远程连接由短期票据 + WebSocket 浏览器终端提供；Telnet 默认禁用，只能由管理员显式开启。
- 原因：满足原始连接需求，同时限制明文协议风险。

## ADR-008：持久化结果以 PostgreSQL 为准

- 状态：`superseded`
- 日期：2026-09-01
- 决策：Redis/Celery 的任务状态不是产品权威状态；设备、告警、任务、文件和审计最终状态全部写入 PostgreSQL。
- 原因：Redis 允许清空和重启，不能承担不可丢失的审计与操作结果。

## ADR-009：不引入告警人工流程

- 状态：`accepted`
- 日期：2026-09-01
- 决策：0.1.0 告警只表达 active/resolved，不提供确认、关闭、派单和通知流程。
- 原因：监控问题展示是必要平台支撑，人工告警流程不在飞书业务功能范围。

## ADR-010：分离可达性、健康和数据新鲜度

- 状态：`accepted`
- 日期：2026-09-01
- 决策：设备是否在线、最后已知硬件健康和指标是否过期分别建模和展示。
- 原因：离线不等于硬件故障，过期数据也不能冒充当前健康。

## ADR-011：最小本地 RBAC

- 状态：`superseded`
- 日期：2026-09-01
- 决策：提供管理员、运维员、观察员、审计员四个内置角色，不做组织/设备范围授权。
- 原因：为危险设备操作提供必要隔离，同时保持单套小型部署简单。

## ADR-012：本地受控文件卷

- 状态：`accepted`
- 日期：2026-09-01
- 决策：0.1.0 使用受控本地卷保存固件、ISO、配置和支持包，不引入对象存储服务。
- 原因：符合单机部署规模；所有文件仍经授权 API、哈希和必要加密。

## ADR-013：原始快照与分层机器契约

- 状态：`accepted`
- 日期：2026-09-01
- 决策：保存已复核飞书原表快照，并将需求白名单、指标、事件、动作、告警、HTTP 端点和错误码拆成 `contracts/` 下七份单一职责机器契约。
- 原因：仅有 51 个标题/键不足以约束后续人和 AI agent 的单位、参数、成功条件和 API 命名，容易产生多套近似实现。
- 结果：CI 必须验证所有引用集合闭合；缺少细化定义时停止而不是猜测。

## ADR-014：能力支持、当前可用性与数据新鲜度分离

- 状态：`accepted`
- 日期：2026-09-01
- 决策：`support_state` 只包含 supported/unsupported/not_configured；`runtime_availability` 单独动态计算 available/temporarily_unavailable；freshness 只包含 unknown/fresh/stale/expired。
- 原因：离线或任务冲突不改变设备固有能力，不支持也不是时间状态；混在一个字段会造成能力表抖动和 UI 误导。
- 结果：缺值/错误写 ObservationError，不以 0、normal 或 unsupported 指标点占位。

## ADR-015：任务与 launch 分流，并持久化防重放边界

- 状态：`superseded`
- 日期：2026-09-01
- 决策：普通人工功能使用 task + DB outbox；连接类功能使用一次性 launch。task 调用设备前持久化 dispatch fence；有副作用 profile 在 fence 后禁止重放，纯读取可新 attempt 重试。高风险任务要求当前会话最近 5 分钟密码复验。
- 原因：连接会话不是持久化硬件变更；Celery 至少一次消息也不能被等同于设备动作可重试。
- 结果：结果不明进入 verification_required，Redis 不承担执行授权或权威状态。

## ADR-016：纠正原始需求的三个派生偏差

- 状态：`accepted`
- 日期：2026-09-01
- 决策：服务器强制重启只保留 `power.cycle`；共享文件夹必须提供百分比使用率；PoE 总功耗必须同时有总功耗、设备预算/比例依据和告警状态。
- 原因：原白名单重复拆出了强制重启动作，并以字节数/瓦数替代了原文要求的“使用率/告警”。
- 结果：旧键 `power.force_restart`、`shared_folder.usage_bytes` 禁止进入实现。

## ADR-017：容量约束采用当前值、变化点和分层保留

- 状态：`superseded`
- 日期：2026-09-01
- 决策：增加 `metric_latest`；状态只记录变化/6 小时检查点；原始点保留 7 天、5 分钟数值聚合 30 天、1 小时数值聚合 180 天；按日分区。
- 原因：70 台 48 口交换机按分钟逐指标写 30 天原始、180 天 5 分钟聚合会与单机 300 GiB 目标冲突。
- 结果：初始采用 20,000 活跃数值序列；后续端口规模复核将基线提高到 30,000。

## ADR-018：私有厂商接口必须以精确版本证据认证

- 状态：`accepted`
- 日期：2026-09-01
- 决策：DSM 非公开管理 API 和 Huawei 型号/VRP 命令/MIB 标记版本边界，归档 API discovery、文档/MIB 散列、脱敏 fixture 和真机回读；不得用其他型号资料或浏览器抓包直接宣称通用支持。
- 原因：公开指南不能覆盖全部原始功能，且同系列不同固件行为会变化。
- 结果：没有精确版本证据的路径只能 experimental/unsupported，不进入正式支持矩阵。

## ADR-019：真机支持按目标、需求和能力键逐项认证

- 状态：`accepted`
- 日期：2026-09-01
- 决策：以 `hardware-targets.json` 固定 0.1.0 的 10 个认证目标，以 JSON Schema 固定证据格式；发布矩阵的唯一覆盖单元为 `target_id + requirement_id + capability_key`，并由独立脚本校验完整笛卡尔覆盖和终态证据。
- 原因：按需求写一条自由格式报告会掩盖同一需求内部分指标/动作未测，弱能力 agent 也可能把自动化、截图或同系列设备资料误当真机支持。
- 结果：当前需要 306 个唯一认证记录；设计阶段不创建假矩阵，发布候选只接受 `hardware_passed` 或具有设备证据及用户书面接受引用的 `unsupported_with_evidence`。

## ADR-020：告警值映射必须穷举且单位一致

- 状态：`superseded`
- 日期：2026-09-01
- 决策：所有参与内置告警的 enum/boolean 指标必须在 `alert-rules.json` 对每个可能值映射为 `no_decision/normal/warning/critical`；百分比预算阈值只作用于 `poe.total_power_percent`，总瓦数仅展示。
- 原因：`severity_from_value` 不能告诉实现者 unknown/absent/rebuilding/off 等状态如何处理，而且以 80/95 百分比阈值比较瓦数会产生错误告警。
- 结果：缺失或未知保持不作判断，不被当作恢复；CI 校验映射无遗漏、无多余值且单位/策略匹配。

## ADR-021：100 台容量基线提高到三万数值序列

- 状态：`superseded`
- 日期：2026-09-01
- 决策：100 台设备按 30,000 条活跃数值序列估算，PostgreSQL/指标 SSD 起点由 300 GiB 调为 500 GiB；仍采用 7 天原始、30 天 5 分钟和 180 天 1 小时分层保留。
- 原因：20 台 48 口核心和 50 台 48 口接入的端口流量/错误、PoE 功耗和光模块数值已经接近两万，原模型没有为服务器、NAS、组件增长和端口满配留下可靠余量。
- 结果：估算点数分别约 3.024 亿、2.592 亿和 1.296 亿；M6 仍必须按实际表/索引/运行开销/临时空间校准，500 GiB 不是免测承诺。

## ADR-022：已撤销的数据库备份方案

- 状态：`superseded`
- 日期：2026-09-01
- 决策：本轮曾设计应用级数据库备份与恢复链路。
- 原因：复核后确认它不是飞书硬件业务功能，也不是 0.1.0 承载核心功能所必需的应用能力。
- 结果：方案全部撤销、未进入实现；现行边界由下一条决策定义。

## ADR-023：0.1.0 不建设数据库备份与灾备能力

- 状态：`accepted`
- 日期：2026-09-01
- 决策：Warden 只定义 PostgreSQL/文件的持久化卷和容器重启语义，不实现数据库备份服务、PITR、灾备编排、备份 UI、RPO/RTO 或备份恢复发布门禁。
- 原因：数据库备份属于部署方基础设施运维，不是飞书硬件业务功能，也不是承载这些功能所必需的应用能力；详细设计会使项目再次偏离硬件监控管理核心。
- 结果：部署方如需备份使用其现有主机/存储策略；Warden 0.1.0 只保证正常运行和容器重建时使用持久化卷，不对此提供产品承诺。

## ADR-024：小型部署使用 PostgreSQL 持久化任务队列

- 状态：`accepted`
- 日期：2026-09-01
- 决策：不使用 Redis、Celery 和消息 outbox。API 在同一 PostgreSQL 事务创建任务与审计；一个 Worker 服务使用 `FOR UPDATE SKIP LOCKED`、租约和数据库约束领取采集/操作任务，并以独立并发池隔离两类工作。
- 原因：单套小型私有部署没有证据证明需要额外 broker；任务与审计已经必须落 PostgreSQL，第二套消息状态增加部署、故障恢复和 agent 实现复杂度。
- 结果：任务行是唯一执行授权；`LISTEN/NOTIFY` 只能用作可丢失唤醒优化。dispatch fence、幂等、互斥和结果不明只核验等安全不变量继续保留。

## ADR-025：当前问题不得使用无来源数值阈值

- 状态：`accepted`
- 日期：2026-09-01
- 决策：`/alerts` 只汇总设备明确上报的当前健康/故障/告警状态、连接离线和数据过期；设备日志事件只保留历史。CPU、内存、容量、错误计数、温度、功率、光模块和 PoE 比例仅展示；没有来源语义时 `alert_policy=none`。
- 原因：先前 80/90、80/95、增量 1、admin/oper 差异和 PoE 比例规则均由设计自行发明，不在飞书需求中，也没有设备阈值证据。
- 结果：PoE 总功耗告警只取 `poe.total_power_alarm`；不提供规则编辑、确认、派单、通知或自动修复。

## ADR-026：平台支撑使用必要性三问

- 状态：`accepted`
- 日期：2026-09-01
- 决策：每个 `PLT-*` 支撑必须说明缺少它会阻断的来源需求、不得形成独立业务对象/工作流、能由部署配置或内部实现解决时不得建设产品页面/API。
- 原因：只限制人工硬件操作仍会允许数据库备份、采集设置、指标出口或通用运维能力以“平台支撑”名义膨胀。
- 结果：删除采集设置页/API、维护模式 Web API 和 Prometheus 端点；维护模式改由宿主机部署命令设置，并在 `TRACEABILITY.md` 固定九项支撑的必要性和禁止扩张边界。

## ADR-027：容量结论必须来自现场验收负载

- 状态：`accepted`
- 日期：2026-09-01
- 决策：不把设计阶段假设的设备数、活跃序列数或磁盘大小写成 0.1.0 产品上限/承诺。默认分层保留继续控制数据增长；生产资源由现场设备/端口/组件、实际发现序列、采集和保留周期、并发用户及文件规模的真实 schema 压测确定。
- 原因：飞书未提供现场数量，固定 100 台、30,000 序列和 500 GiB 会制造错误需求，并可能同时造成过度建设或容量不足。
- 结果：性能和容量测试使用用户确认的部署验收负载及散列，不提供容量规划业务模块。

## ADR-028：采用三类角色和普通只追加审计

- 状态：`accepted`
- 日期：2026-09-01
- 决策：内置角色收缩为管理员、运维员、观察员；审计查看由管理员承担。审计表在应用/数据库权限层只追加，不建设散列链、独立链头、数字签名或外部见证。
- 原因：专职审计员角色和密码学审计结构不是承载来源硬件操作所必需，会把小型设备管理系统扩展成合规平台。
- 结果：危险操作的谁/何时/目标/动作/结果/证据仍完整保留；不声称对抗主机或数据库管理员篡改。

## ADR-029：设备探测失败阶段返回失败令牌而非直接 422

- 状态：`accepted`
- 日期：2026-09-01
- 决策：`POST /device-probes` 对设备侧可观察的失败阶段（网络不可达、TLS/指纹校验失败、认证失败、身份/能力发现失败）返回 200 + 各阶段结果 + 绑定该探测结果的失败 `probe_token`，允许以 `not_ready` 且 `enabled=false` 保存设备；只有平台侧硬错误（未知适配器、SSRF 策略拒绝、参数 schema 不合法）返回 422。
- 原因：API_CONTRACT §4 要求"无论探测成功或失败都会签发绑定探测结果和凭据摘要的 probe_token：失败 token 只能保存为 not_ready 且 enabled=false"，防止绕过连接测试直接启用；把失败阶段打成 422 会使该保存路径不可达。
- 结果：接入流程可按 PRODUCT_DESIGN §4.2 的"连接失败时允许保存为未就绪"执行；成功与失败令牌均绑定探测指纹，保存时重新校验指纹与过期时间。

## ADR-030：只追加审计与任务事件流豁免自动保留清理

- 状态：`accepted`
- 日期：2026-09-02
- 决策：`audit_logs` 与 `operation_task_events` 受数据库触发器与权限 REVOKE 双重只追加保护，0.1.0 的保留清理任务跳过这两张表（记录 `skipped_append_only` 计数），物理清理属于带外 DBA 操作；`operation_tasks` 的 365 天保留同样延后——审计行引用任务且审计不可删除，自动清理会使引用悬空。
- 原因：DATA_MODEL §10 的保留期与"三类角色与普通只追加审计"决策（编号 028）的只追加约束在自动清理路径上冲突；数据库触发器拒绝任何 UPDATE/DELETE（含 owner），应用层自动清理必须绕过触发器才能执行，与只追加安全目标相悖。
- 结果：DATA_MODEL §10 中 audit/operation-task 两行的"自动保留"语义在 0.1.0 解释为"记录清理跳过原因与计数，由部署方按需执行带外清理"；其余保留项（指标分区、滚动聚合、事件、告警、会话）由 warden_app 按 0008/0009 授予的所有权/权限自动清理。

## ADR-031：DSM 错误码映射按官方登录指南语义

- 状态：`accepted`
- 日期：2026-09-03
- 决策：DSM 客户端错误映射以 Synology 官方 DSM Login Web API Guide 为准：`106` = 会话超时（sid 失效）→ 有界重登一次后仍失败则 `authentication_failed`；`105` = 权限不足 → `permission_denied_by_device`；`401/406` = 认证失败 → `authentication_failed`；登录返回 `(Auth,403)` 表示 OTP 需求 → `not_configured missing=otp`（自动化账号应使用专用非 2FA 账号，SECURITY §5）。映射表的每一行都带 `[guide]`/`[sim]` 依据标注；登录类 4xx 的精确真机行为仍属 simulator-DSL，待 M4 目标型号（DS224+/DS225+）真机认证按私有厂商接口精确版本证据决策（编号 018）修正。
- 原因：任务简报中"105/106 → permission"的压缩表述与官方指南（106 为会话超时）及简报自身的测试要求（会话超时→重登一次→authentication_failed）矛盾；实现与测试按指南执行，需要正式决策记录。
- 结果：客户端、模拟器与映射测试统一按本决策执行；未知错误码保留为 `protocol_error` 并在 detail 携带原码，不做猜测映射。

## ADR-032：设备添加向导只列生产适配器

- 状态：`accepted`
- 日期：2026-09-03
- 决策：添加设备向导的适配器下拉按设备类别只列生产注册适配器（服务器 → 五个厂商目标键；群晖 NAS → `nas.synology_dsm`），标注"真机认证待完成"；`fake.simple` 与模拟器旋钮适配器不进向导，保留为开发/API 专用路径（文档注明）。
- 原因：把测试/开发适配器暴露在正式接入向导中会让用户以为存在一条通往"已支持"的捷径；向导呈现的每个适配器都应是对应正式支持路径的入口，正式支持状态由认证矩阵决定。
- 结果：向导与后端注册表分离（注册表仍可注册任意适配器供测试/API 使用）；能力支持状态与认证矩阵继续作为正式支持的唯一声明来源。
